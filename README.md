# MoTv2 — Mine Operations Tool

Инструмент для нанесения шахтной инфраструктуры (связь, позиционирование,
громкое оповещение) на 3D-модель шахты. Фронтенд — тот же single-page
3D-редактор на three.js (`public/index.html`), что и раньше. Добавлен
бэкенд для многопользовательской работы: логин/пароль с ролями, общие
проекты, доступные по адресу вида `http://<сервер>/<project_id>`.

## Структура

- `public/index.html` — фронтенд (парсер STR/DTM, 3D-вьюер, редактор
  кабелей/оборудования/меток/заплаток). Логика самой 3D-модели не менялась —
  изменился только способ загрузки/сохранения состояния (раньше — файл на
  диске, теперь — через API).
- `server/` — бэкенд на Node.js/Express + SQLite (`better-sqlite3`).

## Как это работает

- Проект = отдельная шахта/участок. У каждого проекта свой `id` (латиница,
  цифры, `-`/`_`), доступен по `http://<ip-или-домен>/<project_id>`.
- При открытии страницы фронтенд берёт `project_id` из URL, запрашивает у
  сервера сохранённое состояние (`GET /api/projects/:id/state`) и
  восстанавливает его в 3D-сцене — так же, как раньше это делалось из
  встроенного в HTML JSON.
- Кнопка **"☁ Сохранить в проект"** отправляет текущее состояние
  (кабели/оборудование/метки/заплатки/настройки) на сервер
  (`PUT /api/projects/:id/state`). Кнопка **"💾 Резервная копия HTML"**
  оставлена как и раньше — скачивает standalone HTML-файл локально.
- Если пока вы работали, кто-то другой уже сохранил проект, сервер вернёт
  конфликт версий — появится диалог с выбором: перезаписать или отменить.
  Это защита от молчаливой потери чужих правок (простая модель "общий
  проект + сохранение по кнопке", без сложного realtime-слияния).
- Роли: `viewer` (только просмотр и экспорт CSV/STR), `editor` (полное
  редактирование), `admin` (плюс управление пользователями/проектами через
  `seed.js`).

## Установка на сервер (Docker)

В репозитории есть `server/Dockerfile` и `docker-compose.yml` в корне —
рассчитаны на то, что на сервере уже есть Docker (типичный случай).

```bash
# в корне репозитория
echo "JWT_SECRET=$(openssl rand -hex 32)" > .env
docker compose up -d --build
```

Это поднимет контейнер `mine-ops-tool`, слушающий порт 80 хоста (проброшен
на 3000 внутри контейнера), с данными в именованном Docker-томе
`mine-ops-data` (переживает пересборку/перезапуск контейнера).

### Первый запуск: создать пользователей и проект

Выполняется внутри уже запущенного контейнера:

```bash
docker compose exec mine-ops-tool node seed.js user admin "ваш-надёжный-пароль" admin
docker compose exec mine-ops-tool node seed.js user ivanov "пароль-иванова" editor
docker compose exec mine-ops-tool node seed.js user smirnov "пароль-смирнова" viewer
docker compose exec mine-ops-tool node seed.js project shaft-1 "Шахта №1"
```

`seed.js` можно запускать повторно — существующий пользователь/проект
обновится (пароль/роль/название), а не задублируется.

Проект будет доступен по адресу `http://<ip-сервера>/shaft-1`.

### Обновление на новую версию кода

```bash
git pull origin main
docker compose up -d --build
```

Пользователи/проекты/сохранённые данные не теряются — они лежат в
Docker-томе `mine-ops-data`, а не в самом образе.

### Логи / статус

```bash
docker compose logs -f mine-ops-tool
docker compose ps
```

## Установка без Docker (Node.js напрямую)

Требуется Node.js 18+.

```bash
cd server
npm install
```

### Переменные окружения

- `JWT_SECRET` — обязательна, длинная случайная строка (например,
  `openssl rand -hex 32`). Без неё сервер не запустится.
- `PORT` — порт сервера (по умолчанию 3000).
- `DB_PATH` — путь к файлу SQLite (по умолчанию `server/data/app.db`).
- `TOKEN_TTL` — срок жизни сессии (по умолчанию `12h`).

### Первый запуск: создать пользователей и проект

```bash
cd server
export JWT_SECRET=$(openssl rand -hex 32)
node seed.js user admin "ваш-надёжный-пароль" admin
node seed.js user ivanov "пароль-иванова" editor
node seed.js user smirnov "пароль-смирнова" viewer
node seed.js project shaft-1 "Шахта №1"
```

### Запуск

```bash
JWT_SECRET=... node server.js
```

Проект будет доступен по адресу `http://<ip-сервера>:<port>/shaft-1`.

Для постоянной работы рекомендуется:
- запускать через `pm2`/`systemd`, чтобы сервис поднимался после перезагрузки;
- поставить `nginx` перед Node.js (обратный прокси на порт 80/443 + HTTPS
  через Let's Encrypt), особенно если сервер будет доступен по домену, а не
  по голому IP.

### Добавление новых проектов/пользователей позже

Пользователи — через `seed.js` (см. выше, с `docker compose exec` при
Docker-варианте). Проекты — `node create-project.js <id> "<name>"` (та же
операция, что и `seed.js project`, но отдельным скриптом; см.
`docs/emergency-cli-scripts.md`) или через API (`POST /api/projects`,
только для роли `admin`, токен из `/api/auth/login`).

### Удаление проекта

В интерфейсе такой кнопки нет — только CLI, `node delete-project.js
<projectId> --yes` (сначала без `--yes` — покажет, что будет удалено,
ничего не тронув). См. `docs/emergency-cli-scripts.md`.

## Тесты

```bash
cd server
npm ci

npm test           # backend: unit + integration (node:test), без браузера
npm run test:e2e   # E2E (Playwright, headless Chromium) — требует
                    # npm run playwright:install один раз локально
npm run test:all   # всё вместе
```

На каждый push/PR в `main` тесты гоняются автоматически в CI (GitHub
Actions, `.github/workflows/tests.yml`) — backend и E2E отдельными джобами.

## Известные ограничения текущей версии (MVP)

- Модель совместной работы — "общий проект + сохранение по кнопке" с
  предупреждением о конфликте версий, а не realtime-совместное
  редактирование (как в Google Docs). Можно перевести на WebSocket позже,
  если понадобится.
- Управление пользователями/проектами — через CLI-скрипт `seed.js`, без
  веб-интерфейса администратора.
- Сама 3D-модель шахты (загруженные STR/DTM) хранится в общем JSON-снапшоте
  вместе с кабелями/оборудованием/метками — при очень больших моделях это
  может делать сохранение/загрузку через сеть медленнее, чем раньше через
  локальный файл. При необходимости можно разнести эти два хранилища.
