# Автобэкап БД — настройка офсайт-целей

Расписание, ретеншн локальных копий и обе офсайт-цели (SSH и Google
Drive) настраиваются целиком в **Настройки → Резервное копирование**
(доступно только `admin`) — без консоли на сервере, без `.env`, без
раскладывания файлов руками. Единственное исключение, которое обойти
нельзя — для Google Drive Google требует один разовый шаг в их
собственной Cloud Console (создать OAuth-клиента); дальше всё снова
через наш UI (раздел 2 ниже).

Если ни один из офсайт-вариантов ниже не настроен — автобэкап всё равно
работает и делает **локальные** копии БД (см. `server/data/backups/`,
ротация по `local_retention_count`). Офсайт — это дополнительная защита
на случай, если сгорит сам сервер целиком.

## 1. Другой сервер по SSH

Нужен: SSH-доступ до другого сервера, куда будут копироваться файлы
бэкапа.

1. Сгенерировать отдельную пару SSH-ключей **специально под бэкап** (не
   переиспользуйте свой личный ключ) — на любой машине, откуда удобно,
   не обязательно на сервере MoT:

   ```
   ssh-keygen -t ed25519 -f ./mot-backup-key -N "" -C "mot-backup"
   ```

   Это создаст `mot-backup-key` (приватный) и `mot-backup-key.pub`
   (публичный).

2. Скопировать публичный ключ на сервер-приёмник и разрешить им заходить
   под каким-нибудь пользователем (можно завести отдельного, узкого по
   правам — доступ ему нужен только на запись в одну папку):

   ```
   ssh-copy-id -i ./mot-backup-key.pub <user>@<backup-host>
   ```

   Или вручную дописать содержимое `.pub`-файла в
   `~/.ssh/authorized_keys` пользователя `<user>` на `<backup-host>`.

3. На сервере-приёмнике создать папку под бэкапы, например:

   ```
   ssh <user>@<backup-host> "mkdir -p /home/<user>/mot-backups"
   ```

4. В приложении: **Настройки → Резервное копирование → «Другой сервер по
   SSH»** — заполнить поля **Хост**, **Пользователь**, **Порт** (обычно
   22), **Папка на сервере** (`/home/<user>/mot-backups` из шага 3) и
   вставить в поле **Приватный ключ** содержимое файла `mot-backup-key`
   целиком (откройте его текстовым редактором, скопируйте весь текст —
   от `-----BEGIN ... PRIVATE KEY-----` до `-----END ... PRIVATE
   KEY-----`).
5. Нажать **«Сохранить и проверить»** — приложение сразу пробует
   подключиться и открыть указанную папку; результат проверки покажется
   тут же.
6. Отметить чекбокс «Использовать как цель бэкапа» в блоке «Куда
   копировать» и сохранить настройки.

Приватный ключ после этого хранится в базе данных, не в файлах на диске
и не в `.env` — так же, как Google Drive ниже; форма его больше не
показывает обратно, только даёт заменить или отключить целиком.

## 2. Google Drive

Важно: если ваш Google-аккаунт — обычный **личный Gmail** (не корпоративный
Google Workspace), сервисные аккаунты тут не подходят — у них нет своей
квоты хранилища, и они не могут владеть файлами в обычной папке личного
Диска (это работает только в Shared Drive, а это функция Workspace).
Поэтому здесь — OAuth-авторизация от имени вашего реального аккаунта:
один шаг в Google Cloud Console (это требование самого Google, простого
логина/пароля для Drive API не бывает в принципе — так у всех, кто делает
бэкап на Google Drive), всё остальное — прямо в Настройках приложения.

**Шаг A — один раз в Google Cloud Console** (тут действительно нужна
консоль Google, не наша — это их требование, обойти нельзя):

1. Зайти в [Google Cloud Console](https://console.cloud.google.com/),
   создать проект (или использовать существующий).
2. Включить **Google Drive API**: APIs & Services → Library → найти
   "Google Drive API" → Enable.
3. Настроить экран согласия (если ещё не настроен): APIs & Services →
   OAuth consent screen → User Type **External** → заполнить название
   приложения и свой email → на шаге Test users добавить свой же Google
   email (пока приложение не прошло верификацию у Google, входить могут
   только явно добавленные тестовые пользователи). Важно: пока статус
   приложения — **Testing**, refresh-token протухает через 7 дней, и
   бэкап на Google Drive начнёт падать раз в неделю. Чтобы этого
   избежать, на странице OAuth consent screen нажмите **Publish app**
   (перевод в статус **In production**) — для scope `drive.file`
   (доступ только к файлам, созданным самим приложением, не ко всему
   Диску) верификация у Google не требуется, это чисто переключатель
   статуса, без дополнительных проверок.
4. Создать OAuth-клиент: APIs & Services → Credentials → Create
   Credentials → OAuth client ID → тип приложения **TVs and Limited Input
   devices**. Получите **Client ID** и **Client Secret**.
5. Создать папку на Google Диске под своим обычным аккаунтом, например
   «MoT backups», и взять её ID — часть URL после `/folders/`, когда
   папка открыта в браузере:

   ```
   https://drive.google.com/drive/folders/<ЭТОТ_ID>
   ```

**Шаг B — дальше всё в приложении, без консоли**:

6. Настройки → Резервное копирование → карточка «Google Drive» →
   **Подключить**.
7. Вставить **Client ID**, **Client Secret** и **ID папки на Диске** из
   шага A в форму → **Начать подключение**.
8. Появится ссылка и короткий код — откройте ссылку на любом устройстве
   с браузером (телефон, свой компьютер), войдите под своим
   Google-аккаунтом (тем самым, на чьём Диске папка), введите код,
   разрешите доступ. Страница в Настройках сама дождётся подтверждения
   и покажет «подключено» — обновлять и жать ничего не нужно.
9. Отметить чекбокс «Использовать как цель бэкапа» и сохранить настройки.

Client ID/Secret и refresh-token после этого хранятся в базе данных, не
в `.env`, не в файлах.

Если позже переедете на корпоративный Google Workspace — токен всё
равно продолжит работать, просто там же появится возможность вместо
этого завести Shared Drive.

## 3. S3 (пока не реализовано)

Целевой модуль под S3 ещё не написан (`server/backup/targets/s3.js` не
существует) — сейчас доступны только SSH и Google Drive выше. Когда
понадобится S3, интерфейс уже рассчитан на добавление третьей цели без
переделки остального: нужен будет только новый файл-таргет с тем же
контрактом (`isConfigured()` / `upload()`), что и у `ssh.js`/`gdrive.js`,
плюс соответствующая форма в этом же разделе Настроек (по образцу SSH —
у S3 тоже обычные ключи доступа, без OAuth-плясок).

## Где что лежит — шпаргалка

| Что | Где |
|---|---|
| SSH: хост/пользователь/порт/папка/приватный ключ | БД, таблица `backup_settings` — вводится через Настройки → Резервное копирование |
| Google Drive: client id/secret/refresh-token/folder id | БД, таблица `backup_settings` — вводится через Настройки → Резервное копирование |
| Расписание, ретеншн, вкл/выкл целей | Настройки → Резервное копирование (хранится в БД, таблица `backup_settings`) |
| Локальные копии БД | `server/data/backups/` внутри volume `mine-ops-data` |
| История запусков | Настройки → Резервное копирование → «История» (таблица `backup_runs`) |

Ничего из этого не требует правок `docker-compose.yml` или `.env` —
конфигурация полностью живёт в БД проекта и, соответственно, попадает в
сами бэкапы (восстановление БД из старой копии восстановит и настройки
бэкапа, какими они были на тот момент).

## Если что-то пошло не так

- «Сохранить и проверить» для SSH возвращает ошибку — сначала проверьте
  сообщение (обычно понятное: неверный хост/порт, ключ не подходит,
  сервер отказал в доступе). Убедитесь, что публичный ключ реально
  дописан в `authorized_keys` на сервере-приёмнике и что вставлен именно
  приватный (не публичный) ключ целиком, с строками `BEGIN`/`END`.
- Бэкап на Google Drive падает с `invalid_grant` — обычно означает, что
  refresh-token отозван (доступ приложению отозвали вручную в настройках
  Google-аккаунта, либо OAuth consent screen в статусе Testing и токен
  протух через 7 дней неактивности) — в Настройках нажмите «Отключить»,
  затем «Подключить» заново (шаг B выше).
- При нажатии «Начать подключение» сразу приходит ошибка от Google
  (например "The OAuth client was not found") — проверьте, что Client
  ID/Secret скопированы без пробелов и относятся к клиенту именно типа
  "TVs and Limited Input devices" (шаг A, пункт 4).
- Ошибка **«Не удалось связаться с Google (fetch failed)»** — сервер сидит
  за корпоративным прокси, и у контейнера нет прямого выхода в интернет.
  Проверьте на хосте: `env | grep -i proxy`. Если прокси есть (например
  `http_proxy=http://<хост-прокси>:<порт>`) — укажите его в **Настройки →
  Сеть → Исходящий прокси** (те же значения, что в выводе `env`, просто
  `http://хост:порт`) и нажмите «Сохранить» — применяется сразу, без
  пересборки контейнера. Разные площадки могут указывать там разный
  прокси независимо друг от друга. Если прокси на хосте нет вообще —
  значит у сервера действительно нет исходящего доступа в интернет, и
  Google Drive через OAuth в принципе не заработает, пока это не решат
  сетевые администраторы.

  (Альтернатива для того же самого — переменные `HTTPS_PROXY`/`HTTP_PROXY`
  в `.env` рядом с `docker-compose.yml`: применяются только если поле в
  Настройки → Сеть пустое, и требуют пересборки контейнера при смене —
  полезно как значение по умолчанию, но UI удобнее для разовой настройки
  и для площадок с разным прокси.)

## Деплой после обновления кода бэкапа

```
cd /home/a-khatyushinv/mot-git/repo
git pull origin main
docker compose up -d --build mine-ops-tool backup-worker
```

Оба сервиса нужно пересобрать вместе — `mine-ops-tool` умеет бэкапить по
кнопке «Сделать бэкап сейчас», `backup-worker` — по расписанию из БД;
конфигурацию целей передеплой не трогает, она уже в БД.

### Диагностика: долгая пересборка (минуты вместо секунд)

Если `git pull` подтянул изменения в `server/package.json` (новая или
обновлённая зависимость), `npm install` при следующей сборке выполнится
заново с нуля — это ожидаемо и обычно занимает десятки секунд, даже за
прокси. Но если сборка растягивается на много минут и явно "подвисает"
на шаге `npm install`/`apt-get` — вероятная причина та же корпоративная
сеть, что и в разделе Google Drive выше: `HTTPS_PROXY`/`HTTP_PROXY` в
`environment:` сервиса действуют только для уже ЗАПУЩЕННОГО контейнера,
на саму сборку образа (`apt-get`, `npm install`) не распространяются —
им нужен отдельный проброс через `build.args` в `docker-compose.yml`
(уже сделан для всех четырёх сервисов) из тех же переменных `.env`.
Убедитесь, что `HTTPS_PROXY`/`HTTP_PROXY` заданы в `.env` — тогда они
попадут и в рантайм, и в сборку одновременно, без дополнительных
действий.
