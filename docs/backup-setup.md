# Автобэкап БД — настройка ключей/доступов на сервере

Расписание, количество хранимых локальных копий и включение/выключение
офсайт-целей настраиваются прямо в **Настройки → Резервное копирование**
(доступно только `admin`). Но сами учётные данные для доступа к офсайт-целям
(SSH-ключ, сервисный аккаунт Google) в веб-интерфейсе не хранятся и не
вводятся — это осознанно: секреты живут только на сервере, в файлах и
переменных окружения. Эта инструкция — как их туда положить, один раз, при
первой настройке.

Если ни один из офсайт-вариантов ниже не настроен — автобэкап всё равно
работает и делает **локальные** копии БД (см. `server/data/backups/`,
ротация по `local_retention_count`). Офсайт — это дополнительная защита на
случай, если сгорит сам сервер целиком.

Что нужно сделать один раз на сервере (`/home/a-khatyushinv/mot-git/repo`):

## 1. Другой сервер по SSH

Нужен: SSH-доступ до другого сервера, куда будут копироваться файлы бэкапа.

1. Сгенерировать отдельную пару SSH-ключей **специально под бэкап** (не
   переиспользуйте свой личный ключ):

   ```
   ssh-keygen -t ed25519 -f ./secrets/backup_ssh_key -N "" -C "mot-backup"
   ```

   Это создаст `secrets/backup_ssh_key` (приватный, остаётся на этом
   сервере) и `secrets/backup_ssh_key.pub` (публичный).

2. Скопировать публичный ключ на сервер-приёмник и разрешить им заходить
   под каким-нибудь пользователем (можно завести отдельного, узкого по
   правам — доступ ему нужен только на запись в одну папку):

   ```
   ssh-copy-id -i ./secrets/backup_ssh_key.pub <user>@<backup-host>
   ```

   Или вручную дописать содержимое `.pub`-файла в
   `~/.ssh/authorized_keys` пользователя `<user>` на `<backup-host>`.

3. На сервере-приёмнике создать папку под бэкапы, например:

   ```
   ssh <user>@<backup-host> "mkdir -p /home/<user>/mot-backups"
   ```

4. В `.env` рядом с `docker-compose.yml` (создать файл, если его ещё нет)
   добавить:

   ```
   BACKUP_SSH_HOST=<backup-host>
   BACKUP_SSH_USER=<user>
   BACKUP_SSH_PORT=22
   BACKUP_SSH_REMOTE_DIR=/home/<user>/mot-backups
   ```

5. В `docker-compose.yml` раскомментировать две строки с
   `backup_ssh_key` — по одной у сервисов `mine-ops-tool` и
   `backup-worker` (это один и тот же файл, монтируется в оба места,
   каждому нужен доступ на запуск бэкапа: `mine-ops-tool` — по кнопке
   «Сделать бэкап сейчас», `backup-worker` — по расписанию):

   ```yaml
   - ./secrets/backup_ssh_key:/run/secrets/backup_ssh_key:ro
   ```

6. Пересобрать и перезапустить оба сервиса (см. раздел «Деплой» ниже).

Проверка: в Настройки → Резервное копирование бейдж у «Другой сервер по
SSH» должен смениться с «не настроено на сервере» на «настроено» —
после этого чекбокс включения станет доступен.

## 2. Google Drive

Нужен: сервисный аккаунт Google Cloud (не ваш личный аккаунт — отдельная
техническая учётка) с доступом к Drive API, и папка на Google Диске,
расшаренная этому аккаунту.

1. Зайти в [Google Cloud Console](https://console.cloud.google.com/),
   создать проект (или использовать существующий).
2. Включить **Google Drive API**: APIs & Services → Library → найти
   "Google Drive API" → Enable.
3. Создать сервисный аккаунт: APIs & Services → Credentials → Create
   Credentials → Service Account. Имя — например `mot-backup`. Роль не
   обязательна (доступ будет через шаринг конкретной папки, не через IAM).
4. Создать ключ для этого сервисного аккаунта: открыть его → вкладка
   Keys → Add Key → Create new key → тип **JSON**. Скачается файл
   `<project>-xxxxxxxx.json`.
5. Переименовать и положить его на сервер:

   ```
   cp <скачанный-файл>.json ./secrets/backup_gdrive_sa.json
   ```

6. У сервисного аккаунта в JSON-файле есть поле `"client_email"`
   (что-то вроде `mot-backup@<project>.iam.gserviceaccount.com`) —
   это и есть его "адрес". Зайти на Google Диск под своим обычным
   аккаунтом, создать папку под бэкапы (например «MoT backups»),
   открыть её настройки доступа и расшарить на этот email с правом
   **Редактор** (Editor) — без этого сервисный аккаунт не сможет туда
   писать.
7. Взять ID этой папки — это часть URL после `/folders/`, когда папка
   открыта в браузере:

   ```
   https://drive.google.com/drive/folders/<ЭТОТ_ID>
   ```

8. В `.env` добавить:

   ```
   BACKUP_GDRIVE_FOLDER_ID=<ЭТОТ_ID>
   ```

9. В `docker-compose.yml` раскомментировать две строки с
   `backup_gdrive_sa.json` (у `mine-ops-tool` и у `backup-worker`,
   по той же причине, что и с SSH-ключом выше):

   ```yaml
   - ./secrets/backup_gdrive_sa.json:/run/secrets/backup_gdrive_sa.json:ro
   ```

10. Пересобрать и перезапустить оба сервиса.

Проверка: бейдж «Google Drive» в Настройках должен смениться на
«настроено».

## 3. S3 (пока не реализовано)

Целевой модуль под S3 ещё не написан (`server/backup/targets/s3.js` не
существует) — сейчас доступны только SSH и Google Drive выше. Когда
понадобится S3, интерфейс уже рассчитан на добавление третьей цели без
переделки остального: нужен будет только новый файл-таргет с тем же
контрактом (`isConfigured()` / `upload()`), что и у `ssh.js`/`gdrive.js`,
плюс аналогичные переменные окружения (`BACKUP_S3_*`) и пункт в этом же
разделе Настроек.

## Где что лежит — шпаргалка

| Что | Где |
|---|---|
| Приватный SSH-ключ | `./secrets/backup_ssh_key` (на хосте, никогда не в git — см. `.gitignore`) |
| JSON сервисного аккаунта Google | `./secrets/backup_gdrive_sa.json` (на хосте, никогда не в git) |
| Не-секретные настройки (host/user/папка/folder id) | `.env` рядом с `docker-compose.yml` |
| Расписание, ретеншн, вкл/выкл целей | Настройки → Резервное копирование (хранится в БД, таблица `backup_settings`) |
| Локальные копии БД | `server/data/backups/` внутри volume `mine-ops-data` |
| История запусков | Настройки → Резервное копирование → «История» (таблица `backup_runs`) |

## Деплой после добавления/смены ключей

```
cd /home/a-khatyushinv/mot-git/repo
git pull origin main
docker compose up -d --build mine-ops-tool backup-worker
```

Оба сервиса нужно пересобрать/перезапустить вместе — им обоим нужны
одни и те же переменные окружения и смонтированные секреты (см. таблицу
выше: `mine-ops-tool` умеет бэкапить по кнопке «Сделать бэкап сейчас»,
`backup-worker` — по расписанию из БД).

## Если что-то пошло не так

- Бейдж в Настройках так и показывает «не настроено на сервере» после
  раскомментирования volume и пересборки — скорее всего опечатка в пути
  файла в `.env`/`docker-compose.yml`, либо контейнер не пересобрался
  (проверьте `docker compose ps`, `docker compose logs mine-ops-tool`).
- «Сделать бэкап сейчас» падает с ошибкой чтения ключа — самая частая
  причина: файл `./secrets/backup_ssh_key` (или `backup_gdrive_sa.json`)
  не существовал на хосте **в момент первого запуска контейнера** с
  раскомментированной строкой volume — Docker в этом случае молча
  создаёт на его месте пустую **папку**, а не файл, и чтение падает с
  непонятной ошибкой. Решение: остановить сервисы, убедиться что файл
  реально существует и не является папкой (`ls -la ./secrets/`), при
  необходимости удалить случайно созданную папку и положить файл заново,
  затем поднять сервисы снова.
- Бэкап на Google Drive падает с ошибкой доступа — проверьте, что папка
  расшарена именно на `client_email` из JSON-файла сервисного аккаунта,
  и именно с правом «Редактор», а не «Читатель».
