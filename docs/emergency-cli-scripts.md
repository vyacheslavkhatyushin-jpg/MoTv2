# Аварийные CLI-скрипты — на случай, если UI подведёт

Рабочий справочник по консольным инструментам в `server/*.js`. Все они ходят
напрямую в ту же SQLite-базу, что и сервер (никакого отдельного API), и
рассчитаны на ситуацию, когда обычный интерфейс недоступен, показывает не то,
или не может добраться до конкретной записи (например, объект без `id` —
такие сервер молча пропускает при обычном сохранении, см. ниже).

Запускаются на сервере внутри контейнера:

```
docker compose exec mine-ops-tool node <script>.js <аргументы>
```

(имя сервиса — как в вашем `docker-compose.yml`; если контейнер называется
иначе, подставьте своё имя вместо `mine-ops-tool`.)

## Объекты модели: кабели / оборудование / метки / заплатки

Три скрипта работают с одним и тем же снимком проекта
(`project_state.snapshot_json`) через общий модуль `server/lib/snapshot-store.js`.

### `dump-snapshot.js` — резервная копия перед рискованной правкой

```
node dump-snapshot.js <projectId> [outFile]
```

Сохраняет текущий снимок проекта в JSON-файл (по умолчанию —
`server/data/<projectId>-backup-<timestamp>.json`, то есть внутри volume, не
теряется вместе с контейнером). Делайте это **перед** любым использованием
`delete-object.js` — если правка окажется ошибочной, снимок можно будет
восстановить вручную.

```
node dump-snapshot.js apk
node dump-snapshot.js apk data/apk-backup-before-cleanup.json
```

### `list-objects.js` — найти объект и его id/index

```
node list-objects.js <projectId> <cables|equipment|marks|patches> [labelSubstring]
```

Печатает по одной строке JSON на объект: `index` (позиция в массиве), `id`,
`label`, `createdBy`, `createdAt`, и для кабелей/меток — `position`/`nodeCount`.
`labelSubstring` — необязательный фильтр по подстроке в подписи (регистр
неважен).

```
node list-objects.js apk marks
node list-objects.js apk marks "ODF-24"
node list-objects.js apk equipment "MAP"
```

Если у части объектов нет `id` (см. ниже), скрипт печатает предупреждение —
такие объекты можно опознать и удалить только по `index`.

`list-marks.js <projectId> [labelSubstring]` — более старая команда, оставлена
для совместимости; делает ровно то же самое, что `list-objects.js <projectId>
marks [labelSubstring]`.

### `delete-object.js` — удалить один объект напрямую из БД

```
node delete-object.js <projectId> <cables|equipment|marks|patches> <objectId>
node delete-object.js <projectId> <cables|equipment|marks|patches> --index <N>
```

Удаляет объект и увеличивает версию снапшота — так же, как обычное сохранение
из редактора, чтобы не путать с параллельной правкой из интерфейса.
`--index N` (номер берётся из вывода `list-objects.js`) — единственный
надёжный способ адресовать объект **без** `id`: обычное сравнение по id для
такой записи бессмысленно.

```
node list-objects.js apk marks "ODF-24"     # найти id или index
node delete-object.js apk marks m_abc123
node delete-object.js apk marks --index 4
```

**Когда это нужно.** Обычное удаление через интерфейс не срабатывает, если в
3D наложены друг на друга две записи с одинаковой подписью (кликом
разбираются не всегда — история с дублирующейся меткой «Муфта ODF-24»,
15.09.2026: пользователь стабильно удалял через UI один и тот же объект, а
второй с той же подписью оставался незамеченным), либо если объект вообще
лишён `id` (найдено дважды на проекте `apk`, 15.09.2026: сначала метка, потом
кабель и оборудование — `JSON.stringify` молча убирает `id: undefined` при
сохранении, поэтому такие записи не показывают id даже в обычных списках).

**Причина id-less объектов установлена (17.09.2026)**: все они датируются
11–15.09.2026 — переходным периодом до коммита "Merge concurrent edits
per-object instead of whole-snapshot overwrite" (15.09), который впервые
завёл стабильные id при восстановлении объектов из снапшота (`overrides?.id
?? makeObjectId(...)`) и сам по-id мёрдж (`mergeCollection`) на сервере. До
этого коммита `create*`-функции при КАЖДОМ восстановлении объекта из
снапшота генерировали id заново (`"patch" + (++objSeq)`), не оглядываясь на
то, что уже было сохранено — id-less записи, созданные в этот период, дожили
до сегодня как есть. Новых так появляться не должно: `mergeCollection`
отклоняет upsert/delete без id с 15.09, а клиент с этого же коммита сохраняет
id стабильно при каждом восстановлении. Разовая находка задним числом на
проекте `apk`, 17.09.2026: одна id-less заплатка method:"link" ("Труба-связка
5", тоже из этого периода) при каждом открытии редактора и последующем
сохранении порождала НОВУЮ копию с собственным id (сам код восстановления
исправно генерирует стабильный id для новой копии — так и было задумано —
но саму id-less запись при этом никак не убирает, потому что заменить/удалить
её нечем адресовать), из-за чего за примерно неделю накопилось 28 дублей —
см. `find-idless-objects.js` ниже, чтобы проверить, нет ли такого же
залежавшегося экземпляра в других проектах/коллекциях.

### `find-idless-objects.js` — найти id-less объекты сразу во всех проектах

```
node find-idless-objects.js
```

Проверяет разом все проекты и все 4 коллекции (`cables`/`equipment`/`marks`/
`patches`), печатает `project`/`collection`/`index`/`label` для каждой
найденной id-less записи — быстрее, чем гонять `list-objects.js` по каждому
проекту и каждой коллекции вручную. Только показывает, ничего не удаляет —
для самой чистки см. `delete-object.js --index` выше. При удалении
нескольких объектов из одной коллекции одного проекта удаляйте по одному,
начиная с **самого большого** индекса (после каждого удаления индексы этой
коллекции сдвигаются).

## Проекты и пользователи

### `list-projects.js`

```
node list-projects.js
```

Список всех проектов на сервере: `id`, `name`, `createdAt`, версия
сохранённого состояния, кем и когда сохранялось в последний раз.

### `list-users.js`

```
node list-users.js
```

Список всех пользователей и их ролей (`viewer`/`editor`/`admin`). Хеши
паролей не печатаются — это только просмотр.

### `seed.js` — создать/изменить пользователя (включая сброс пароля) или проект

```
node seed.js user <username> <password> <viewer|editor|admin>
node seed.js project <id> <name>
```

`user` создаёт нового пользователя либо перезаписывает пароль и роль
существующего (полезно, если все admin-аккаунты разом потеряли пароли).
`project` делает то же самое, что и `create-project.js` ниже (создаёт проект
или переименовывает существующий) — оставлен для совместимости, но для
проектов удобнее отдельный `create-project.js`, симметричный
`delete-project.js`.

```
node seed.js user admin "S3cure-Pass!" admin
```

### `create-project.js` — создать проект (или переименовать существующий)

```
node create-project.js <id> <name>
```

Разовая операция администратора, кнопки на это в интерфейсе нет. `id`
становится частью URL (`/<id>`) — используйте короткий понятный слаг; сам
`id` переименовать нельзя (он часть уже сохранённых ссылок), только `name`.
Если проект с таким `id` уже есть, команда просто обновит его название.

```
node create-project.js shaft-1 "Шахта №1"
```

### `delete-project.js` — безвозвратно удалить проект целиком

В интерфейсе кнопки удаления проекта нет намеренно — слишком легко нажать по
ошибке и потерять сразу всё (модель, ЗИП, историю аварий, отчёты по
фонарям...). Единственный способ — эта команда.

```
node delete-project.js <projectId>          # только показать, что будет удалено
node delete-project.js <projectId> --yes    # удалить по-настоящему
```

Без `--yes` скрипт ничего не трогает — только печатает сводку (сколько
объектов модели, событий мониторинга, позиций/заявок ЗИП, отчётов по
фонарям и т.д. будет стёрто), чтобы можно было свериться перед реальным
удалением. Технически связанные таблицы объявлены с `ON DELETE CASCADE`
(см. `db.js`), поэтому под капотом это один `DELETE FROM projects`.

Перед реальным удалением, если в проекте есть модель, имеет смысл сохранить
её снимок на всякий случай:

```
node dump-snapshot.js shaft-old
node delete-project.js shaft-old            # свериться со сводкой
node delete-project.js shaft-old --yes      # удалить
```

Действие необратимо — отмены или корзины нет.

## Реестр ЗИП

Отдельного аварийного CLI для ЗИП пока нет — при необходимости прямой правки
таблиц `zip_items`/`zip_requests`/`zip_movements` используйте `sqlite3` по
файлу БД (`server/data/app.db`) вручную; модуль сознательно устроен так, что
все операции (приход/выдача/корректировка) уже проходят через append-only
`zip_movements`, поэтому источник правды по остаткам восстановим даже после
прямого вмешательства.
