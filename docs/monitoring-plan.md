# Мониторинг оборудования шахты — план

Рабочий документ архитектуры. Полная оформленная версия (с диаграммой и таблицами) опубликована отдельно; здесь — содержание для истории и справки прямо в репозитории.

## Зачем

Модель шахты в MoTv2 уже содержит инвентарь оборудования (координаты, IP, тип). Мониторинг не заводит отдельную базу устройств, а надстраивается над этими же объектами:

- подсветка аварийных участков/оборудования на 3D-модели;
- append-only лог аварий/отключений (по аналогии с логом удалений);
- счётчик людей на считывателях IILB/ISIB;
- единая точка правды поверх трёх независимых источников данных.

## Источники по типам оборудования

| Тип | Источник | Что получаем | Частота |
|---|---|---|---|
| IILB, ISIB | SPPD (система HFT), WebSocket | online/offline, RSSI, TxRx, прошивка, число людей на точке | реальное время (push) |
| MAP, WiFi | Ping (+SNMP по мере подтверждения) | доступность; опционально аптайм/состояние портов | 30–60 сек |
| CAM | Ping | доступность | 30–60 сек |
| TEL | Ping шлюза (SPA/ATA) | доступность шлюза — сразу для обоих телефонов на нём | 30–60 сек |
| MLA, MPS, MPC, MTU, MVSA, MBU, FS, Статив, Муфта ODF | — | без сети, не мониторится на этом этапе | — |
| Кабели | — (идея на будущее) | обрыв участка — косвенно, по потере связи с оборудованием на концах | — |

## Интеграция с SPPD (изначально называли «FlexCom»)

Система на `10.20.99.7` — связка сервисов: **SPPD** (телеметрия сетевых устройств), **SBeacon** (трекинг бирок персонала), **GSA** (общешахтная сирена/эвакуация — не используется в этом мониторинге). `10.20.99.7` — адрес только для одной шахты, у каждой из трёх (apk/ipk/opk) свой физический сервер SPPD со своим логином/паролем — см. «Модель данных» ниже, per-project настройка, а не общий адрес.

**Аутентификация** — стандартная Django-сессия:
```
GET  /login/   → cookie csrftoken + csrfmiddlewaretoken из HTML
POST /login/   → username, password, csrfmiddlewaretoken, next="/", login=""
     ← 302, Set-Cookie: sessionid=...
```

**Телеметрия** — `ws://10.20.99.7/sppd/v1/ws/stream`, сообщения приходят по частям на один `Addr`:
```json
{"WSM_TYPE":"SB_EVENT","WSM_DATA":{"Addr":"3934","Id":232,
  "TxRx":{"Rx":98,"Tx":201,"UTime":1789449325},
  "State":{"UTime":1789449325,"OnLine":true}}}
```

**Счётчик людей** — `ws://10.20.99.7/sbeacon/v1/ws/stream`:
```json
{"WSM_TYPE":"NOFTAG","WSM_DATA":{"Addr":"1000",
  "NOfTag":265,"NOfTagUnit":256,"NOfMan":254,"NofVehicle":2,"utime":1789449376}}
```
Открытый вопрос: общая ли нумерация `Addr` у SPPD и SBeacon для одного физического считывателя — **подтверждено на реализации**: `Addr` из SB_EVENT совпадает с `Addr`/`addr` из NOFTAG/REG_TAG для одного и того же считывателя.

**Регистрация метки** — там же, в потоке SBeacon: отдельное дискретное событие (не задокументировано изначально, обнаружено уже после деплоя по реальным логам) — используется для точной "вспышки" вместо приближения по приросту счётчика:
```json
{"WSM_TYPE":"REG_TAG","WSM_DATA":{"tag_id":8524,"unit_id":7939,"device_id":216,
  "tid_addr_433":38429,"addr":"3555","utime":1789467841}}
```
Обратите внимание: поле адреса тут `addr` в нижнем регистре — не `Addr`, как в остальных типах сообщений.

**Справочник устройств** — `GET /sppd/v1/insiteexpert/device/get/all` → `{ devices: { "63": { address:"2341", name:"ВВ ворота3", TypeDevice:4099, ... } } }`. `address` — то же, что `Addr` в потоке.

## Ping/SNMP

- **Ping** — обязательный базовый уровень для MAP/WiFi/CAM/TEL, при ~200 устройствах — пакетно (`fping`), а не последовательными процессами.
- **SNMP** — опционален, добавляется по мере подтверждения по каждому типу. Проверено: community `public` работает (протестировано на коммутаторе MOXA EDS-408A). На MAP/WiFi/CAM напрямую — ещё не проверено.

## Модель данных

Новые поля в объекте `equipment` (внутри JSON-снапшота проекта):
```
monitorMethod   "none" | "ping" | "snmp" | "sppd"
snmpCommunity   string | null
snmpProfile     string | null
sppdAddress     string | null   — только для IILB/ISIB
```

Новые таблицы SQLite:
```sql
monitor_status (
  project_id, equipment_id,
  state, last_checked_at, last_change_at, latency_ms,
  person_count, vehicle_count, raw_metrics_json,
  PRIMARY KEY (project_id, equipment_id)
)

monitor_events (
  id, project_id, equipment_id, equipment_label,
  from_state, to_state, started_at, ended_at, duration_sec,
  acknowledged_by, acknowledged_at
)

monitor_tag_pulses (
  id, project_id, equipment_id, created_at
)   -- эфемерная очередь "новая метка зарегистрировалась", см. Этап 4

-- Подключение к SPPD — своё для каждого проекта (apk/ipk/opk — три разных
-- физических сервера), настраивается через UI (админ, кнопка "⚙ SPPD" в
-- редакторе), не переменными окружения воркера.
project_sppd_config (
  project_id PRIMARY KEY, base_url, username, password,
  updated_by, updated_at
)
```

## План по этапам

1. ✅ **Поля и таблицы** — новые поля в `equipment`, таблицы `monitor_status`/`monitor_events`, UI для admin.
2. ✅ **Ping-коллектор** — отдельный процесс (`server/monitor/ping-worker.js`), базовая доступность для MAP/WiFi/CAM/TEL.
3. ✅ **Страница `/<project>/monitoring`** — отдельная страница (не вкладка в редакторе): тот же 3D-движок и снимок проекта, но урезанный интерфейс — только зелёное/красное неоновое свечение на модели, список активных аварий и история, без редактирования. Живые обновления по WebSocket-каналу `/api/monitor/ws`. В обычном редакторе — ссылка «📡 Мониторинг», на странице мониторинга — ссылка «✏️ Редактор» обратно. Панель вкладки «Мониторинг» дополнена группировкой по системам: кнопки «Все / ВОЛС / LFC / АО / Телефония / ВН» фильтруют списки «Кабели» и «Оборудование» (сгруппированы по типу/форме, с чекбоксами вкл/выкл, 🎯 переходом и ✨ подсветкой), «Метки» показываются без фильтрации. Силовой кабель принадлежит всем пяти системам; MAP и Статив — сразу нескольким (отмечены бейджем ×N). Отдельного блока «Шахта» на странице нет — модель показывается как есть, с тем же составом видимых слоёв, что и в редакторе. Вверху панели — блок «Активные аварии» фиксированной высоты со своей прокруткой.
4. ✅ **SPPD-коллектор** (`server/monitor/sppd-worker.js`, отдельный процесс) — каждая шахта (apk/ipk/opk) подключается к своему физическому серверу SPPD, поэтому воркер не global-конфигурируется через env, а раз в `SPPD_CONFIG_REFRESH_MS` (по умолчанию 60 с) перечитывает таблицу `project_sppd_config` и держит по независимому "сайту" (сессия + два WS + список целей) на каждый настроенный проект — добавление/смена/удаление конфигурации подхватывается без перезапуска процесса. Настройка — через UI (кнопка «⚙ SPPD» в редакторе, только admin; `GET/PUT/DELETE /api/projects/:id/monitor/sppd-config`; пароль на GET не отдаётся, только факт, что он задан). На каждый сайт: Django-логин (`/login/`, csrftoken/sessionid), два постоянных WebSocket-подключения — `sppd/v1/ws/stream` (SB_EVENT → online/offline + TxRx/прошивка в `raw_metrics_json` для оборудования с `monitorMethod:"sppd"` и заданным `sppdAddress`, обычно IILB/ISIB) и `sbeacon/v1/ws/stream` (NOFTAG → `person_count`/`vehicle_count`). Реконнект с бэкоффом на разрыв соединения, переопрос списка целей каждые 30 с, обновление логина раз в 6 ч. Белая вспышка на регистрацию метки — точно, по событию `REG_TAG` (обнаружено в реальном потоке уже после деплоя, раньше приближали по росту счётчика `NOfTag`): воркер пишет разовую запись в `monitor_tag_pulses`, `server.js` на очередном цикле рассылки подбирает свежие и шлёт клиентам `{type:"tagPulse"}`, клиент вызывает уже готовый `spawnMonitorTagPulse()`. **Проверка на живой системе** (apk, 15.09.2026): логин и оба WebSocket-подключения работали сразу, но сервер не рассылал данные в них — по одному из скриншотов DevTools подтвердили, что сама система жива и данные (`SB_EVENT`/`NOFTAG`/`REG_TAG`) реально идут в браузерной сессии; добавили заголовки `Origin`/`Referer` на апгрейде WebSocket (гипотеза: Django-приложение проверяет их так же, как Referer/CSRF на обычных запросах) — ждём подтверждения после передеплоя, что это и было причиной. Заодно подтверждён открытый вопрос из плана: нумерация Addr у SPPD и SBeacon для одного считывателя — общая.
5. **SNMP поверх ping** — по мере проверки community/OID на конкретных устройствах.
6. **Сводная `/monitoring`** — по всем проектам.
