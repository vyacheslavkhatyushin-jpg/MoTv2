# Мониторинг оборудования шахты — план

Рабочий документ архитектуры. Полная оформленная версия (с диаграммой и таблицами) опубликована отдельно; здесь — содержание для истории и справки прямо в репозитории.

## Зачем

Модель шахты в MoTv2 уже содержит инвентарь оборудования (координаты, IP, тип). Мониторинг не заводит отдельную базу устройств, а надстраивается над этими же объектами:

- подсветка аварийных участков/оборудования на 3D-модели;
- append-only лог аварий/отключений (по аналогии с логом удалений);
- счётчик людей на считывателях IILB/ISIB;
- единая точка правды поверх трёх независимых источников данных.

## Источники по типам оборудования

| Тип | Источник | Что получаем | Частота |
|---|---|---|---|
| IILB, ISIB | SPPD (система HFT), WebSocket | online/offline, RSSI, TxRx, прошивка, число людей на точке | реальное время (push) |
| MAP, WiFi | Ping (+SNMP по мере подтверждения) | доступность; опционально аптайм/состояние портов | 30–60 сек |
| CAM | Ping | доступность | 30–60 сек |
| TEL | Ping шлюза (SPA/ATA) | доступность шлюза — сразу для обоих телефонов на нём | 30–60 сек |
| FS | FieldSense/FlexAlertTTE, WebSocket (`ws://<host>/fatte/api/ws/fieldsense`) | online/offline (`status` в сообщении `SENSOR`), заряд батареи | реальное время (push) |
| MLA, MPS, MPC, MTU, MVSA, MBU, Статив LFC, Статив АО, PoE, ГО, Муфта ODF | — | без сети, не мониторится на этом этапе | — |
| Кабели | — (идея на будущее) | обрыв участка — косвенно, по потере связи с оборудованием на концах | — |

## Интеграция с SPPD (изначально называли «FlexCom»)

Система на `10.20.99.7` — связка сервисов: **SPPD** (телеметрия сетевых устройств), **SBeacon** (трекинг бирок персонала), **GSA** (общешахтная сирена/эвакуация — не используется в этом мониторинге). `10.20.99.7` — адрес только для одной шахты, у каждой из трёх (apk/ipk/opk) свой физический сервер SPPD со своим логином/паролем — см. «Модель данных» ниже, per-project настройка, а не общий адрес.

**Аутентификация** — стандартная Django-сессия:
```
GET  /login/   → cookie csrftoken + csrfmiddlewaretoken из HTML
POST /login/   → username, password, csrfmiddlewaretoken, next="/", login=""
     ← 302, Set-Cookie: sessionid=...
```

**Телеметрия** — `ws://10.20.99.7/sppd/v1/ws/stream`, сообщения приходят по частям на один `Addr`. **Важно**: `WSM_DATA` на проводе — это JSON, закодированный ЕЩЁ РАЗ как строка (`"WSM_DATA":"{\"Addr\":...}"`), а не готовый объект — `sppd-worker.js` разбирает его вторым `JSON.parse()`; без этого `data.Addr` всегда `undefined`, и все сообщения молча отбрасываются (реальный баг, найденный на apk 15.09.2026, из-за которого весь Этап 4 сначала выглядел так, будто вообще не работает — Origin/Referer и разбор по WSM_TYPE были настоящими и нужными фиксами, но именно это ело все сообщения поверх них):
```json
{"WSM_TYPE":"SB_EVENT","WSM_DATA":"{\"Addr\":\"3934\",\"Id\":232,
  \"TxRx\":{\"Rx\":98,\"Tx\":201,\"UTime\":1789449325},
  \"State\":{\"UTime\":1789449325,\"OnLine\":true}}"}
```

**Счётчик людей** — `ws://10.20.99.7/sbeacon/v1/ws/stream`:
```json
{"WSM_TYPE":"NOFTAG","WSM_DATA":{"Addr":"1000",
  "NOfTag":265,"NOfTagUnit":256,"NOfMan":254,"NofVehicle":2,"utime":1789449376}}
```
Открытый вопрос: общая ли нумерация `Addr` у SPPD и SBeacon для одного физического считывателя — **подтверждено на реализации**: `Addr` из SB_EVENT совпадает с `Addr`/`addr` из NOFTAG/REG_TAG для одного и того же считывателя.

**Регистрация метки** — там же, в потоке SBeacon: отдельное дискретное событие (не задокументировано изначально, обнаружено уже после деплоя по реальным логам) — используется для точной "вспышки" вместо приближения по приросту счётчика:
```json
{"WSM_TYPE":"REG_TAG","WSM_DATA":{"tag_id":8524,"unit_id":7939,"device_id":216,
  "tid_addr_433":38429,"addr":"3555","utime":1789467841}}
```
Обратите внимание: поле адреса тут `addr` в нижнем регистре — не `Addr`, как в остальных типах сообщений.

**Справочник устройств** — `GET /sppd/v1/insiteexpert/device/get/all` → `{ devices: { "63": { address:"2341", name:"ВВ ворота3", TypeDevice:4099, ... } } }`. `address` — то же, что `Addr` в потоке.

## Интеграция с FieldSense (FlexAlertTTE, поиск обрыва кабеля)

Тот же физический сервер и тот же логин/пароль, что у SPPD (`project_sppd_config` переиспользуется, отдельной настройки нет) — но это **другой бэкенд** ("fatte"), не тот же Django-процесс, что SPPD. Страница `/FlexAlertTTE/fieldsense/` отдаёт только пустой каркас таблицы "Датчики" (`#`, Антенна, Место установки — без статуса/времени/заряда, они пустые в исходном HTML) — первая версия воркера пробовала опрашивать эту страницу по HTTP и регуляркой разбирать HTML, но статус всегда приходил пустым: все живые данные подгружает браузерный JS через WebSocket, а не сервер при рендере страницы.

Реальный источник — `ws://<host>/fatte/api/ws/fieldsense`, тот же конверт `{WSM_TYPE, WSM_DATA}`, что у SPPD/SBeacon:
```json
{"WSM_TYPE":"SENSOR","WSM_DATA":{"bs_id":1,"sensor_id":119,"status":0,"battery_lvl":0}}
```
`sensor_id` — тот же номер, что колонка "#" в таблице (сопоставление с оборудованием — по `fsAddress`, тот же принцип, что `sppdAddress` у SPPD). `status`: `1` — "На связи", `0` — "Нет связи" (подтверждено на живой системе) — доверяем этому значению напрямую, как `OnLine` у SPPD: `applyOnlineState` (импортирован из `sppd-worker.js`, не дублируется) красит статус сразу и debounce'ит запись аварии по своему отдельному per-project порогу `fs_fail_duration_sec` (не общий со SPPD — `applyOnlineState` принимает необязательный `failDurationMsOverride`, `fieldsense-worker.js` всегда передаёт своё значение).

**Авторизация этого WS — отдельная кука `PHPSESSID`** (PHP-сессия), а не Django `sessionid`/`csrftoken`, которые использует SPPD. На живой системе она приходит тем же логином (POST `/login/` выдаёт её вместе с остальными куками) — `login()` в `sppd-worker.js` раньше явно сохранял только `csrftoken`/`sessionid` и терял всё остальное; это исправлено (теперь возвращаются все куки с ответа). На случай, если `PHPSESSID` всё же не пришёл тем же логином, `fieldsense-worker.js` дополнительно "прогревает" сессию GET-запросом на `/FlexAlertTTE/fieldsense/` и подхватывает `PHPSESSID` из его `Set-Cookie`, если он появится там.

## Ping/SNMP

- **Ping** — обязательный базовый уровень для MAP/WiFi/CAM/TEL, при ~200 устройствах — пакетно (`fping`), а не последовательными процессами.
- **SNMP** — опционален, добавляется по мере подтверждения по каждому типу. Проверено: community `public` работает (протестировано на коммутаторе MOXA EDS-408A). На MAP/WiFi/CAM напрямую — ещё не проверено.

## Фонари — работоспособность по отчёту "Текущие местоположение"

Отдельный модуль (`/<project>/lamps`, `server/routes/lamps.js`) — не живой поток, а ручная загрузка отчёта SPPD/SBeacon (.xls/.xlsx, тот же отчёт, что даёт список тегов/местоположений персонала). Тег шахтёра = фонарь; "исправен", если была регистрация на любом считывателе не позже `lamp_fail_after_hours` (по умолчанию 24 ч, настраивается per-project через "⚙ Пороги") назад **от времени, указанного в самом отчёте**, а не от текущего времени сервера — иначе статус "плыл" бы при открытии старого отчёта из истории.

Формат отчёта отличается между шахтами: apk отдаёт `.xlsx` с одним полем ФИО и меткой "Не задан / &lt;id&gt;" вместо номера фонаря (фонарь = личный тег), ipk/opk — старый бинарный `.xls`, где ФИО разбито на Фамилия/Имя/Отчество и есть отдельный реальный номер фонаря "Св.№", не равный таб.№. `server/lib/lampReportParser.js` разбирает оба формата одним кодом: строка заголовков ищется по ключевым словам (не по фиксированной позиции), дата отчёта — регуляркой по дате-времени в первых строках файла (не по тексту подписи, он тоже разный). Библиотека `xlsx` (SheetJS) читает и `.xls`, и `.xlsx`; у неё есть открытые CVE (prototype pollution, ReDoS) без исправления в npm-версии — риск принят осознанно (загрузка только editor/admin, лимит размера файла 15 МБ), альтернативы на момент реализации нет.

Технический нюанс: как минимум один реальный экспорт apk писал в `.xlsx` заведомо неверный `<dimension>` (например "A1:I7" при факте ~1000 строк) — SheetJS доверяет этому диапазону и молча обрезает результат; парсер пересчитывает `!ref` листа из реальных заполненных ячеек перед чтением.

Каждая загрузка — отдельная строка в `lamp_reports` (+ `lamp_records` на объект), история не перезаписывается — это даёт тренд (спарклайн % исправности по последним загрузкам) и позволяет открыть любой прошлый отчёт, а не только последний. `is_broken` считается один раз при загрузке и не пересчитывается задним числом при смене порога.

## Модель данных

Новые поля в объекте `equipment` (внутри JSON-снапшота проекта):
```
monitorMethod   "none" | "ping" | "snmp" | "sppd" | "fs"
snmpCommunity   string | null
snmpProfile     string | null
sppdAddress     string | null   — только для IILB/ISIB
fsAddress       string | null   — только для FS, номер "#" из таблицы "Датчики" на /FlexAlertTTE/fieldsense/
```

Новые таблицы SQLite:
```sql
monitor_status (
  project_id, equipment_id,
  state, last_checked_at, last_change_at, latency_ms,
  person_count, vehicle_count, raw_metrics_json,
  PRIMARY KEY (project_id, equipment_id)
)

monitor_events (
  id, project_id, equipment_id, equipment_label,
  from_state, to_state, started_at, ended_at, duration_sec,
  acknowledged_by, acknowledged_at
)

monitor_tag_pulses (
  id, project_id, equipment_id, created_at
)   -- эфемерная очередь "новая метка зарегистрировалась", см. Этап 4

-- Подключение к SPPD — своё для каждого проекта (apk/ipk/opk — три разных
-- физических сервера), настраивается через UI (админ, кнопка "⚙ SPPD" в
-- редакторе), не переменными окружения воркера.
project_sppd_config (
  project_id PRIMARY KEY, base_url, username, password,
  updated_by, updated_at
)
```

## План по этапам

1. ✅ **Поля и таблицы** — новые поля в `equipment`, таблицы `monitor_status`/`monitor_events`, UI для admin.
2. ✅ **Ping-коллектор** — отдельный процесс (`server/monitor/ping-worker.js`), базовая доступность для MAP/WiFi/CAM/TEL.
3. ✅ **Страница `/<project>/monitoring`** — отдельная страница (не вкладка в редакторе): тот же 3D-движок и снимок проекта, но урезанный интерфейс — только зелёное/красное неоновое свечение на модели, список активных аварий и история, без редактирования. Живые обновления по WebSocket-каналу `/api/monitor/ws`. В обычном редакторе — ссылка «📡 Мониторинг», на странице мониторинга — ссылка «✏️ Редактор» обратно. Панель вкладки «Мониторинг» дополнена группировкой по системам: кнопки «Все / ВОЛС / LFC / АО / Телефония / ВН» и фильтруют списки «Кабели»/«Оборудование» (сгруппированы по типу/форме, с чекбоксами вкл/выкл, 🎯 переходом и ✨ подсветкой), и — по нажатию — реально переключают видимость слоёв на самой 3D-модели: остаются только кабели/оборудование выбранной системы (плюс сама модель шахты и все метки, которые ни к одной системе не привязаны и переключателем не трогаются), «Все» возвращает видимость всех слоёв. Силовой кабель принадлежит всем пяти системам, поэтому виден при любом выборе. Отдельного блока «Шахта» на странице нет — модель показывается как есть. Вверху панели — блок «Активные аварии» фиксированной высоты со своей прокруткой.
4. ✅ **SPPD-коллектор** (`server/monitor/sppd-worker.js`, отдельный процесс) — каждая шахта (apk/ipk/opk) подключается к своему физическому серверу SPPD, поэтому воркер не global-конфигурируется через env, а раз в `SPPD_CONFIG_REFRESH_MS` (по умолчанию 60 с) перечитывает таблицу `project_sppd_config` и держит по независимому "сайту" (сессия + два WS + список целей) на каждый настроенный проект — добавление/смена/удаление конфигурации подхватывается без перезапуска процесса. Настройка — через UI (кнопка «⚙ SPPD» в редакторе, только admin; `GET/PUT/DELETE /api/projects/:id/monitor/sppd-config`; пароль на GET не отдаётся, только факт, что он задан). На каждый сайт: Django-логин (`/login/`, csrftoken/sessionid), два постоянных WebSocket-подключения — `sppd/v1/ws/stream` (SB_EVENT → online/offline + TxRx/прошивка в `raw_metrics_json` для оборудования с `monitorMethod:"sppd"` и заданным `sppdAddress`, обычно IILB/ISIB) и `sbeacon/v1/ws/stream` (NOFTAG → `person_count`/`vehicle_count`). Реконнект с бэкоффом на разрыв соединения, переопрос списка целей каждые 30 с, обновление логина раз в 6 ч. Белая вспышка на регистрацию метки — точно, по событию `REG_TAG` (обнаружено в реальном потоке уже после деплоя, раньше приближали по росту счётчика `NOfTag`): воркер пишет разовую запись в `monitor_tag_pulses`, `server.js` на очередном цикле рассылки подбирает свежие и шлёт клиентам `{type:"tagPulse"}`, клиент вызывает уже готовый `spawnMonitorTagPulse()`. **Проверка на живой системе** (apk, 15.09.2026): логин и оба WebSocket-подключения работали сразу, но сервер не рассылал данные в них — по одному из скриншотов DevTools подтвердили, что сама система жива и данные (`SB_EVENT`/`NOFTAG`/`REG_TAG`) реально идут в браузерной сессии; добавили заголовки `Origin`/`Referer` на апгрейде WebSocket (гипотеза: Django-приложение проверяет их так же, как Referer/CSRF на обычных запросах) — после передеплоя данные пошли, гипотеза подтвердилась. Заодно выяснилось: тип сообщения не привязан к пути, как предполагали названия (`/sppd/...` vs `/sbeacon/...`) — на практике `SB_EVENT` приходил на "sbeacon"-соединение, а `REG_TAG` на "sppd" — воркер теперь разбирает оба канала одинаково, по `WSM_TYPE`. Заодно подтверждён открытый вопрос из плана: нумерация Addr у SPPD и SBeacon для одного считывателя — общая. `person_count`/`vehicle_count` выведены на странице мониторинга: суммарно вверху панели (👤/🚚, только если хоть у одного объекта реально есть данные) и по каждому IILB/ISIB отдельно, рядом со статус-точкой в списке «Оборудование».

SPPD — push-модель без активного опроса (в отличие от ping-worker, который сам стучится и получает явный отказ), поэтому пропавший считыватель просто перестаёт слать `SB_EVENT`, а не присылает явную ошибку. Добавлена проверка "протухания": раз в `SPPD_STALE_CHECK_MS` (по умолчанию 30 с) воркер проверяет каждую настроенную цель, и если от её `Addr` не было ни одного сообщения дольше порога — сам переводит в `state:"down"` ("Нет связи") с записью в `monitor_events`, как при обычном отключении. У никогда не отвечавшего оборудования есть тот же запас времени с момента старта воркера (не мгновенная красная вспышка до первого ответа).

4.1 ✅ **Дашборд «История аварий»** (`/<project>/monitoring/stats`, отдельная лёгкая страница без Three.js) — карточка на каждую систему (ВОЛС/LFC/АО/Телефония/ВН) со статус-пилюлей, тремя KPI (аварий за период/среднее устранение/uptime%) за выбранный диапазон (24ч/7д/30д), спарклайном за фиксированные 7 дней и списком активных+устранённых аварий. Клик по карточке открывает таблицу со всеми событиями этой системы (`GET /api/projects/:id/monitor/events?system=&range=`), с deep-link через `?system=`. Кнопка «📊 Статистика по авариям» — на странице `/<project>/monitoring`, под заголовком. Старый плоский блок «История» там убран, его заменяет эта страница.

4.2 ✅ **Пороги фиксации аварии — per-project** (таблица `project_monitor_thresholds`, `GET/PUT/DELETE /api/projects/:id/monitor/thresholds`, кнопка «⚙ Пороги» в редакторе, только admin). Раньше это были глобальные на все проекты сразу переменные окружения воркеров; теперь у каждой шахты можно настроить отдельно. Ключевой принцип: **статус на дашборде/3D-модели всегда живой** (сырой результат последнего пинга/сигнала — "нет связи" красит красным немедленно), а вот **«авария» как событие в `monitor_events`** (то, что считает аптайм/среднее время устранения/попадает в историю) **фиксируется только после устойчивого простоя** — эти две вещи раньше были одним и тем же моментом, теперь разнесены по времени:
   - **Таймаут пинга** (`ping_timeout_sec`, по умолчанию 1 с) — сколько ждать ответа на ping.
   - **Простой до фиксации аварии** (`ping_fail_duration_sec`, по умолчанию 300 с = 5 мин, в UI — в минутах, 0 = фиксировать сразу) — `ping-worker.js` пишет сырой up/down в `monitor_status` на каждом тике независимо от этого порога; отдельно, в памяти процесса, отслеживает момент начала текущей непрерывной серии неудач (`downSince`, сбрасывается любым успешным пингом) и открывает `monitor_events` только когда простой набрал этот порог — `started_at` события при этом берётся от реального начала простоя, а не от момента фиксации. Короткий флап (короче порога) вообще не попадает в историю аварий, хотя мигает на дашборде как обычно.
   - **Молчание SPPD до "Нет связи"** (`sppd_stale_after_sec`, по умолчанию 120 с) — то же самое значение, что раньше было только в `SPPD_STALE_AFTER_MS`. Это порог ОБНАРУЖЕНИЯ — раньше него узнать о пропаже нечем в принципе (SPPD либо явно шлёт `State.OnLine:false`, либо просто замолкает без явной ошибки), поэтому статус на дашборде красится сразу по истечении именно этого порога — более раннего "сырого" сигнала для тишины не существует.
   - **Простой до фиксации аварии — SPPD** (`sppd_fail_duration_sec`, по умолчанию 300 с = 5 мин, в UI — в минутах, 0 = сразу) — а вот ФИКСАЦИЯ аварии как события в `monitor_events` теперь так же разнесена по времени с покраской, как и у ping, причём для ОБОИХ путей обнаружения "down" сразу: и явного push `State.OnLine:false` от считывателя (раньше `applyOnlineState()` открывала событие в тот же момент, что красила статус — теперь красит сразу, а событие открывает только после этого порога), и обнаруженной тишины (`markStaleAsDown()`, вызывается каждые `SPPD_STALE_CHECK_MS` пока тишина длится). Общий для обеих веток счётчик `downSince` в памяти процесса (`trackDownAndMaybeOpenEvent()`), `started_at` события — от реального момента начала простоя, не от момента срабатывания порога.

   - **Простой до фиксации аварии — FieldSense/FS** (`fs_fail_duration_sec`, по умолчанию 300 с = 5 мин, в UI — в минутах, 0 = сразу) — отдельная от SPPD настройка, тот же принцип: статус красится сразу по `SENSOR`-сообщению, событие в `monitor_events` — после этого простоя.

   Отсутствие строки в `project_monitor_thresholds` для проекта = используются дефолты выше — старое поведение "фиксировать сразу" воспроизводится настройкой простоя в 0 мин, если кому-то он нужен.
